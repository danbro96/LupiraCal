# LupiraCal — agent notes

- **Purpose**: web UI over LupiraCalApi's REST surface (REST only, no sync-protocol paths). Visualizes the temporal backbone: calendar Class/Kind, ItemKind details, Prompt/Action payloads, completeness, availability segments, curation, tags, metadata, relations.
- **Monorepo (npm workspaces)**: root `package.json` hoists the toolchain; workspaces = `packages/domain` (`@lupira/cal-domain` — shared pure TS, consumed as source, no deps, never import generated DTO types there), `packages/tokens` (`@lupira/cal-tokens` — design tokens: light/dark `ColorScheme`, semantic palettes, the map layer palette (`map`), spacing/typography/breakpoint; same purity rules; consumers re-type records against generated enums as the drift tripwire; new workspaces must also be added to the Dockerfile's COPY + `npm ci -w` lines), `apps/web`, and `apps/mobile` (Expo 57 "Lupira Calendar", package `com.lupira.calendar`, scheme `lupiracalendar`; layering `domain→data→sync→state→ui`, own orval gen against the BFF prefixes, Authentik client `lupira-cal-mobile`; program tracker in `docs/mobile/milestones.md`). Root scripts fan out (`npm run lint|typecheck|test`) or delegate (`dev|build|gen:api`).
- **Shape**: .NET 10 BFF (`src/LupiraCalBff`) + Vite/React 19 + MUI SPA (`apps/web`) in one image. BFF owns Authentik OIDC (`lupira-cal` client, PKCE, no secret), cookie `__Host-lupira-cal`, Duende token refresh, YARP → the seven upstream roots (prefix stripped, bearer attached). No anonymous surface. Dev: auto-auth + `X-Dev-User` forwarded (CalApi Development accepts it).
- **`/depz`** (BFF's own, not proxied): non-gating availability report, one anonymous `readyz` probe per `ReverseProxy:Clusters` entry named by registry service (`Dependencies/DependencyTargets`); `X-Probe-Key` = `Depz:ProbeKey`, blank = off.
- **The proxy is an allowlist.** `src/LupiraCalBff/exposed.json` names every `VERB /path` the BFF forwards; `Proxy/ProxyRoutes` builds `ReverseProxy:Routes` from it at startup as a config source (one exact template per path, `Match.Methods` pinned) — `dotnet run --project src/LupiraCalBff -- --routes` prints the table, and `UpstreamSpecMerger` filters the published document by the same file — so the proxy and the client cannot disagree, so neither can be hand-edited. Clusters stay in appsettings; a config source is what lets `LoadFromConfig` and the `ApiPrefixes` fence read the routes unchanged. It lists only what the clients actually call; an operation with no caller is not exposed. Adding an endpoint = a line in `exposed.json`; the merge prints anything upstream that isn't listed, and throws if a listed one no longer exists. **Never widen a route to `{**catch-all}`** — that forwards whatever the upstream adds under it, unreviewed. Two exceptions: `exposed.static` (geo-api `/basemap`, GET-only file subtree — glyph ranges can't be enumerated) and `exposed.device` (location-api `/ingest/location*`, mounted at the upstream path with no transform, `AuthorizationPolicy: Anonymous`). **Ingest is Anonymous because only location-api holds the device keys** — the BFF gates on `DeviceKey {32hex}.{64hex}` well-formedness (`Auth/DeviceKeyHeader`, 401 before the proxy so a device never gets an OIDC redirect) and the YARP transform stands aside so the header reaches the upstream untouched. It stays out of the merged spec: the generated client can only express Bearer, which is why the uploader is hand-written. **Web and both mobile apps talk only to the BFF** — no client may call an upstream origin. Deliberately unreachable: `/mcp` (proxying it tunnels past the Cloudflare edge exclusion), `/internal/*`, `/dav-backend/*`, `/depz`, `/openapi/v1.json`, `/scalar`, `/pingz`, comms `/ingest`, tasks `/shared/{token}` and `/users/directory` — the ingest and share-link surfaces authenticate with a device key, service credential or bearer token, not the family session. An API path matching no route 404s (`ApiPrefixes` fence in `Program.cs`); without it the SPA fallback answers 200/HTML and a dead route looks alive.
- **The BFF owns its own contract.** `src/LupiraCalBff/OpenApi/UpstreamSpecMerger` reconstructs the BFF's OpenAPI document from the seven upstream specs it proxies (committed + embedded under `src/LupiraCalBff/upstream/`, allowlisted by `src/LupiraCalBff/exposed.json`): prefixes each cluster's paths with its BFF mount, dedupes identical schemas and namespaces the rest. `BffDocumentTransformer` grafts it onto the ASP.NET document, so **every `dotnet build` writes `openapi/LupiraCalBff.json`** — the spec is a build artifact, not something a script manufactures — and the BFF serves `/openapi/v1.json` + `/scalar` (authenticated: the document is the whole internal API map). It merges on the JSON DOM, not `OpenApiDocument`, because renaming a colliding schema means retargeting its `$ref`s and the typed model exposes referenced nodes read-only. **Refreshing an upstream spec**: copy it into `src/LupiraCalBff/upstream/`, then `dotnet run --project src/LupiraCalBff -- --normalize-specs src/LupiraCalBff`, then regenerate any C# client (`dotnet tool run kiota …`, pinned in `.config/dotnet-tools.json`), then build. Two passes because a generated C# client compiles *into* the BFF, so the BFF cannot produce the generator's input in the same build.
- **`upstream-normalized/` is the C# generator's input, not the published contract.** `TODO(kiota)`: the whole pass goes once a kiota release carries [the oneOf-null fix](https://github.com/microsoft/kiota/pull/8064) (merged 2026-08-19, unreleased as of 1.34.1) — the specs are correct, OpenAPI 3.1 has no other way to say "nullable reference". `NullableRefNormalizer` collapses `oneOf: [{type:"null"}, {$ref:X}]` to a bare `$ref` (72 sites) because Kiota models every `oneOf` as a composed type — left alone it emits a wrapper class plus a junk member type per property (39 each in cal) and reads become `item.Status?.ItemStatus`. **Never normalize the published document**: orval uses the null branch and emits `status?: null | ItemStatus`, so collapsing there silently strips the null from the TS types. `normalized-specs.test.ts` pins both halves.
- **The BFF can serve an endpoint itself, and that is how one leaves the proxy.** `Endpoints/` declares the route, `Handlers/` holds the logic, `Dtos/` the response shape, and `Upstream/<Cluster>/` a Kiota client generated from `upstream-normalized/` (scoped with `--include-path`, so only the operations a handler calls are generated). **`SessionTokenHandler` is what makes this work** — the YARP transform only runs on proxy routes, so without it a handler calls upstream unauthenticated; it mirrors the transform exactly (caller's own Bearer forwarded, `X-Dev-User` in dev, otherwise the session's access token) and Kiota is deliberately given an `AnonymousAuthenticationProvider` so there is one auth path, not two. Base addresses come from `ReverseProxy:Clusters`. **Kiota throws on non-2xx where the proxy passed the status through**, so a handler must map 404/403 itself or an upstream 404 reaches the SPA as a 500. Migrating an endpoint = declare it, drop its `exposed.json` line, and **extend the matching `useInvalidate` predicate** — a BFF path does not share the upstream prefix, so a mutation would otherwise leave it stale. First one: `GET /api/contacts/{id}/context`, which replaced two calls the pane could only make after learning the contact's `addressBookId`.
- **API client is generated, once, in `packages/api`** (`@lupira/cal-api`), from `openapi/LupiraCalBff.json`. That is what makes query keys collision-free: orval derives them from the path, and `/pingz` lived in four specs, `/items` in two. **Never hand-prefix a query key again.** Both flavours are generated over one set of models — `query/*` (react-query) for anything read straight off the server, `fetch/*` for callers that own their caching. Each app installs its own `setApiTransport` (`packages/api/src/transport.ts`); paths already carry their prefix, so no mutator prepends anything. Refresh with `npm run gen:api` (→ `npm run gen -w packages/api`) after any upstream endpoint change; never hand-edit `packages/api/src/generated/`. Every `/me` is dropped but contact's, which alone carries `contactId` — the BFF owns identity at `/auth/user`. Numerics generate as plain `number` (the APIs set `NumberHandling.Strict`) — never re-add `Number()` coercion at use sites.
- **UI stack (web)**: MUI v9 (Emotion; per-component default imports; v9 API only — `slots`/`slotProps`, `sx`). Theme = `ui/theme/muiTheme.ts`: `createTheme({cssVariables: {colorSchemeSelector: 'media'}, colorSchemes})` fed from tokens (teal primary), system-driven dark, breakpoint `md: 821` = the phone breakpoint (`useIsPhone` wraps `useMediaQuery`). **Every token comes from the theme**: palette (incl. custom `border` + `text.subtle` + `warning`/`success`) emits `--mui-palette-*`; the domain relation accents emit as `--cat-*` via `MuiCssBaseline` styleOverrides, sourced from `@lupira/cal-tokens/contactCategories`. **Styling lives in the theme, then `sx` — there is no bespoke stylesheet.** `index.css` is 39 lines: Tailwind's two entry points, an `@theme inline` that re-exports `--cat-*` as `cat-*` utilities, three element resets, and `.map-canvas` (maplibre-gl.css forces `position:relative` on its own wrapper, so the host must size as a flex child). Tailwind 4 is present for utilities on non-MUI elements and for vendor DOM you can only reach with an arbitrary variant. **Never set `modularCssLayers`** — MUI 9.3.1 declares `mui.*` layers it never emits, so the declared order governs nothing and `sx` silently loses to component styles. Emotion stays unlayered and outranks Tailwind, which is safe only because no element carries both. **Two `className` hooks are deliberate and load-bearing**: `.contact-row` (so the pin reveals on row hover) and `.map-canvas`. **MUI v9 narrowed system props** — `Stack` takes only `direction`/`spacing`/`divider`/`useFlexGap`/`sx`, and `Typography` ignores `color` for palette paths; put both in `sx`, and use `useFlexGap` on any wrapping `Stack`. Vendor stylesheets (maplibre, xyflow) are unlayered and so outrank every layer: overriding their own rules needs `!`. Shared layout primitives live in `ui/components/`: `WrapRow`, `DrawerSection`, `Page`/`PageHead`, `Row`/`RowName`, `panes.tsx`. Forms = react-hook-form (`Controller`-wrapped MUI fields; ContactEditForm gates its 8-endpoint fan-out by payload comparison, not dirtyFields). Mutation errors → `useSnackbar()` (SnackbarHost); field validation stays inline. Detail cards share `drawer/DetailDrawer.tsx`. Build splits a `vendor-mui` chunk (rolldown `advancedChunks`).
- **UI stack (mobile)**: react-native-paper 5 (MD3) themed from tokens via `ui/theme/paperTheme.ts` (+ adapted React Navigation themes); dark mode via `useColorScheme`. The whole palette rides on the Paper theme and **`useColors()` is the app's only colour hook — never Paper's `useTheme()` directly** (same rule as tasks-mobile/assistant-mobile). Two files are the documented exception, each because it needs an MD3 slot the estate palette has no equivalent for: `SyncBanner` (errorContainer) and `MapScreen` (elevation ramp). Confirm flows use `useConfirm()` (ConfirmDialogHost) and transient failures `toast()`/`toastError()` from the `feedback/` leaf (host: `ToastHost`, Paper `Snackbar`) — same shape as the sibling apps; `useUnsavedGuard` keeps `Alert.alert` (fires inside `beforeRemove`). `Button`/`ConfirmDialog` are byte-identical to the sibling apps' copies. Text inputs use the `Input` wrapper in `ui/components/form.tsx` (Paper `TextInput`, outlined+dense, label prop — `Field` is only for non-text controls), which keeps a column-rhythm `marginTop` where the siblings' `TextField` carries a row-layout `flex: 1`. No hex literals except white text over calendar-colored backgrounds. `debug/log.ts`, `DebugLogScreen` and `DeveloperScreen` are shared with the sibling apps — a redacted zustand buffer plus Sentry breadcrumbs, gated in Settings on the `debugEnabled` pref. Tabs are Calendar/Contacts/Map/Photos, each showing the native header; Settings is a pushed stack screen reached by `SettingsButton` in the tab navigator's `headerRight`. Calendar's period nav and Contacts' search sit in `ScreenToolbar` under that header. Program tracker: `docs/mobile/milestones.md` (M13).
- **Screens** are `ui/screens/XScreen.tsx` with a named export. The three lazy routes (`MapScreen`, `PlacesScreen`, `PhotosScreen`) keep `export default` because `React.lazy` needs one; the filename still matches the symbol. `ContactsLayout` lives in `ui/navigation/` — it is routing structure, not a screen. Mobile's root navigator is `ui/navigation/RootStack.tsx`, as in the sibling apps.

- **Mobile keeps hand-written hooks over the generated *fetchers* — do not swap them for the generated *hooks*.** Its query keys are the sync engine's invalidation contract: `sync/reactivity.ts` invalidates by domain aggregate (`['photos']`, `['contacts']`, `['items']`, `['occurrences', monthKey]`), react-query matches by prefix, and every hook nests under the aggregate it belongs to — including cross-API ones, so `['photos','event-links']` is a **cal-api** relations call filed under photos. No route prefix expresses that grouping. Route-keyed hooks would simply stop matching, silently, leaving stale screens. The mobile `QueryClient` also defaults to `staleTime: Infinity, retry: false` for the local mirror, which network-backed hooks each override — generated hooks would inherit it and fetch once, forever. The web has no sync engine and no such contract, which is why the generated hooks fit there and not here.

- **What is shared, and what stays per-app.** Pure logic the two apps agree on lives in `packages/domain` or `packages/tokens`; a hook's query key, gating and return shape stay per-app (mobile's keys are the sync engine's invalidation contract), and so do the MapLibre layer components — same expressions, but per-renderer wrappers and touch-vs-pointer sizes. `useMapData` and `usePhotoLibrary` already delegate to `mapFeatures`/`photoFormat`; what remains in them is DTO-vs-mirror-row adaptation, which is not drift.

- **Stay in step with the sibling Lupira frontends.** Same components, theme wiring and layout;
  match what they already do rather than inventing a local shape. Shared files stay byte-identical.
- **Topbar**: every root screen shows the navigator's native header — title from `options.title`,
  actions from `headerRight`, and the cog is the shared `SettingsButton`. Never `headerShown: false`
  on a root screen. A screen's own controls (search, period nav, filters) go in `ScreenToolbar`,
  a row *under* the header, not instead of it. Status strips render nothing when healthy.
- **Header actions are declared in the navigator's `options`**; `useLayoutEffect` + `setOptions` only
  when the action gates on screen state (a Save enabled only when dirty).
- **Picker choice is by option-set shape, not by app**: `SegmentedPicker` (Paper `SegmentedButtons`)
  for a fixed 2–5 required set; `ChoiceChips` (a wrapping Paper `Chip` row) for dynamic/unbounded sets
  and for clearable single-select. Each lives only where it is used — copy it across when a second app
  needs one, and keep the copies byte-identical.
- **Layering**: `data → state → ui` (+ leaf `config/`), enforced by eslint-plugin-boundaries v7. Domain logic lives in `@lupira/cal-domain` (pure + vitest-tested: grid math, occurrence column layout, recurrence-rule/fire prose, partial dates, task-deadline rules (`tasks`), basemap style handling (`mapStyle`), place-lookup batching (`places`)), importable from every layer; its purity is enforced by its own eslint config.
- **Grids are hand-rolled** (no calendar lib): `GET /items?from&to` returns recurrence-expanded occurrences; grids still fan out one query per visible calendar although the occurrence DTO now carries `calendarIds` (single-query refactor pending). Proposed items ghost from `GET /calendars/{id}/proposed`; availability band joins occurrence → item detail for status.
- **Map** (`/locations`, nav label "Map"): lazy route (`React.lazy` — maplibre-gl stays in its own chunk). Data: occurrences+contacts hydrate placeIds via geo `POST /places/lookup` (`usePlaceCoords`, key `/geo-api/places/lookup` — a hand-written query over a POST, which orval generates as a mutation); GPS via `/location-api` prefix (`@lupira/cal-api/query/location`). Basemap = geo-api `/basemap/style.json?theme=` + pmtiles (client rewrites URLs absolute in `mapStyle.ts`; fallback wash when unprovisioned). Layer palette is `@lupira/cal-tokens/map`, dataviz-validated — don't tweak hues casually; Unknown activity = dashed gray, never a fifth hue. MapLibre/React glue is centralized in `useGeoJsonLayer` (re-adds sources/layers on styledata). **maplibre-gl v6 worker gotcha**: its default worker URL (sibling of the entry module) 404s under bundlers, and bundling the worker yourself (`?worker&url`) emits an EMPTY file in prod (tree-shaken — maplibre's `sideEffects` allowlist; symptom: FF "Attempting to create a Worker from an empty source", gray map, zero `sourcedata`). Fix in place: `sync:maplibre` script vendors `maplibre-gl-worker.mjs` + `maplibre-gl-shared.mjs` verbatim into `public/maplibre/` (gitignored, runs predev/prebuild) + `setWorkerUrl('/maplibre/maplibre-gl-worker.mjs')` in `MapCanvas.tsx` — don't remove either half. A missing basemap *sprite* is equally fatal (style stuck loading); `loadMapStyle` Range-probes the pmtiles and falls back to `fallbackStyle` when assets are unprovisioned. **Mobile Map tab** (`apps/mobile/src/ui/screens/MapScreen.tsx`): `@maplibre/maplibre-react-native` — MapLibre Native reads `pmtiles://https://` sources directly (no worker/protocol shims); the style document handling (absolutize URLs, Range-probe the tiles, fall back) is `@lupira/cal-domain/mapStyle`, and each app's `mapStyle.ts` supplies only its transport — cookie on web, bearer on mobile; bearer for native tile/glyph/sprite requests rides `TransformRequestManager.addHeader` with a stable id (in-place token rotation) and a `match` scoped to the BFF origin — never let that header reach presigned or third-party URLs. Layers split into `apps/mobile/src/ui/map/layers.tsx`; chrome (layers sheet + locate FAB) in `MapChrome.tsx`. **The phone is the estate's only GPS uploader** — `sync/locationRecorder.ts` records under an Android foreground service into `location_fix_queue`, `sync/locationUploader.ts` drains it. Ingest is the one call that does NOT ride the BFF: it authenticates with `Authorization: DeviceKey …`, which the BFF's OIDC-only policy rejects, so it posts straight to `LOCATION_INGEST_URL` and must stay hand-written (the OpenAPI doc declares only a Bearer scheme). NDJSON lines are snake_case and must never carry principal/device ids — the server rejects the whole line. Cadence adapts to speed but **accuracy stays High in every profile**: Balanced is ~100 m, above the server's 50 m cutoff, and still-mode is exactly when visits (80 m / ≥8 min) are detected — a cheap still profile silently yields zero visits. Cadence changes call `startLocationUpdatesAsync` again rather than stop+start (Android 12+ forbids restarting a location FGS from the background). The task is registered in `index.ts`, not from a React effect — a headless restart has no App component.
- **Photos** (web `/photos`, reached from BottomNav's More; mobile Photos tab): day-grouped, cursor-paged grid over `/photo-api/photos` — sort `TakenAtDesc`/`TakenAtAsc` (the cursor encodes its direction and the server rejects a mismatch), filters kind/located/place/status/event. `GET /photos/stats` feeds the year/month timeline (a pick filters to that span rather than scrolling — an unloaded month would mean paging through everything since) and the failed chip; `POST /photos/lookup` hydrates relation ids in one call. The event filter resolves client-side (edges → lookup → `@lupira/cal-domain/photoFilter`), never by paging the list. Both grids multi-select for bulk link/delete, and one event picker (`LinkEventDialog` / `LinkEventSheet`, window `captureWindow`) serves a single photo and a selection. The mobile viewer's Save goes through `restorePhoto`, which files the copy as already uploaded in `photo_upload_queue` — it is a new MediaStore asset with a fresh creation time, so the next scan would otherwise upload it again. **Presigned URLs rotate their signature**, so image caches must key on the asset id (`recyclingKey` on mobile) and `staleTime` stays well inside the 24 h thumb expiry; `originalUrl` is single-asset-only and short-lived, so the viewer fetches it for the page in view alone. HEIC originals are served untranscoded — neither client can decode them, both fall back to the thumbnail. Photo↔event links are cal-api `Relation`s with `toKind: 'photo'` (`GET /relations/edges?toKind=photo` returns the whole map in one call); candidates come from items around `takenAt` and are always confirmed, never auto-linked — the window is `@lupira/cal-domain/photoWindow` so both clients suggest the same set, and the item drawer/detail screen offers the photos taken while an event was happening. **Duplicates are detected server-side, twice**: a surrogate `(takenAt, sizeBytes, contentType)` match at declare returns `Status: Duplicate` with no upload URL (so a second phone never transfers the bytes), and the worker hashes the original it already streams for the thumbnail and marks late duplicates, deleting their objects. A duplicate owns no bytes, points at the canonical via `duplicateOfId`, is excluded from listings unless `status=Duplicate` is asked for by name, and is deleted along with its canonical — it can never be promoted. Map ↔ gallery cross-links ride URL/route params: `/locations?at=<lon>,<lat>` (mobile: the Map tab's `at`) flies to a photo, and `?from=&to=` day bounds (YMD, the map's own vocabulary) filter the gallery to a pin's day.
- **Comms topics**: a contact's finished topics from LupiraCommsApi (`/comms-api` BFF prefix, `@lupira/cal-api/query/comms`, hook `useContactTopics`). Reached only from the contact detail's "Comms" link → `/contacts/:contactId/topics/:topicId?`, one `React.lazy` pane (`ContactTopicsPane`, default export) that lists topics or renders one topic's messages — nothing is fetched, and no comms code is loaded, until that link is clicked. comms has no topic↔participant link, so `contactId` narrows on `Topic.LastConversationId`: a topic answers for the conversation its latest message landed in. Ask for `status=Closed&status=Released` (`SETTLED_TOPIC_STATUSES`) — the closer moves topics on within a sweep, so filtering on `Closed` alone finds nothing. Labels are the opening message's first words until the titling pass runs (`titled: false` → `topicHeadline` quotes them).
- **Task deadlines**: third grid source from LupiraTasksApi (`/tasks-api` BFF prefix, hook `useTaskDeadlines` over the generated `useListItems`). Open non-Cancelled tasks with `dueAt` in range render as all-day chips — which tasks qualify, due-day pinning, overdue and the deep link are `@lupira/cal-domain/tasks`; `fromTask` (web) and `taskDeadlineRows` (mobile) only shape the row (`fromTask`; the deadline/overdue treatment is an sx branch in WeekGrid/MonthGrid, not a class); click → `?task=<listId>:<itemId>` TaskCard with `lupiratasks://task/<listId>/<itemId>` deep link + tasks.lupira.com list fallback; Sidebar "Deadlines" toggle gates the fetch. Tasks-api dev listens on 8080 (Kestrel section beats ASPNETCORE_URLS).
- **/items page**: global list/search across all readable calendars in one infinite query (`useItemSearch`, skip/take paging, filters in URL params: q/tag/cal/category/status/range/from/to/parent); rows open the shared `?item=` drawer. Search covers accepted items only (never proposed). Hierarchy: one visual level — children nest under their parent's first loaded occurrence (`domain/itemTree.ts`; parent absent → flat row with `↳ parent` chip); `?parent=<id>` drills into all children (API defaults parentId searches to all-time); drawer has a HierarchyPanel (distinct from RelationsPanel's cross-API edges).
- **Known API gaps** (UI works around): no owner-list endpoint (share panel is action-only); all-day dates/kind/timezone not updatable over REST; recurrence can't be cleared (null = keep); kind details read-only except Availability.
