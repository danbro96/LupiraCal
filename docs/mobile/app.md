# Mobile app (apps/mobile)

Shared Paper conventions: `~/Nextcloud/Familj/DevOps/Guides/frontend-estate.md`. Program tracker: [milestones.md](milestones.md). This file holds LupiraCal's specifics.

## UI stack specifics

- Paper is themed from tokens via `createPaperThemes` (`@danbro96/lupira-expo-paper`, called in `ui/theme/paperTheme.ts`; + adapted React Navigation themes); dark mode via `useColorScheme`.
- Feedback: `toast()` / `toastError()` from `@danbro96/lupira-expo-feedback` (host: the expo-paper `ToastHost`, Paper `Snackbar`); hold-to-copy (place tiles, reach rows) is its `copyText()`. `useUnsavedGuard` keeps `Alert.alert` (it fires inside `beforeRemove`).
- Text inputs use the expo-paper `TextField` (label prop, `fieldGap` between stacked fields); `ui/components/Field` wraps only non-text controls.
- No hex literals except white text over calendar-coloured backgrounds.
- A place renders as `ui/components/PlaceTile` everywhere (name, address, meta line, `ui/map/MiniMap` thumbnail — a texture-mode, gesture-less `MapView`, so detail screens only, never lists — framed by place type via `@danbro96/lupira-domain-maps/mapZoom`; tap → the Maps app at that point). Tags render as `TagRow` text, never chips.
- Detail screens carry no container padding: Paper rows and subheaders bring their own 16dp, other blocks take `spacing.lg`.
- Icons: `ui/icons.ts` maps concepts to `MaterialIcons`.
- Root navigator is `ui/navigation/RootStack.tsx`.

## Tabs, settings, calendar

- Tabs are Calendar/Contacts, each showing the native header. Settings is a pushed stack screen reached from the `AccountButton` avatar (it opens Settings; sign-out is in Settings' Account section) in the tab navigator's `headerRight`: sections whose rows show each area's state (warning colour when it needs you) and open `CalendarSettings` / `NotificationSettings` / `AndroidSettings`. The map, photo library, GPS upload and camera-roll backup live in the sibling apps Lupira Maps and Lupira Photos; Cal opens them through `ui/openSibling` (`lupiramaps://`, `lupiraphotos://`, https fallback).
- Contacts' search sits in `ScreenToolbar` under the header; it matches names, nicknames and tags. Below it a chip row of the mirrored contact groups filters the list to one group's members; a long-press opens `GroupDetail` (members, × removes, Add member searches the mirror's contacts of the group's address book). Pulling the list down runs a sync (`state/usePullToSync`, disabled offline). The week lanes have none: their ScrollView is in RNGH's gesture arbitration (pinch, page swipe).
- Contact edit (new contacts too) has an Addresses section: one `ui/places/AddressForm` per residency — type, then street / postcode / city / country with matching addresses below (`useAddressLookup`, structured typeahead, online). Picking a match creates the place (`placeCommands`) and shows it on a mini-map; Adjust pin, Change, Moved out (today) and Remove follow. Unresolved, it offers "Same as <household member>" chips (`householdHomes`), Use existing place (`PlaceSearchSheet`, residency context; predictions add recent addresses from the mirror's residencies, `recentResidencies`) and Pick on map. A half-typed address blocks Save (`addressSaveError`). Save diffs the rows into `contact.residency.*` ops (`domain/addressRows`), queued offline like the contact's own; labels and moved-in dates stay on the web.
- Contact detail shows the contact's groups as chips under the name (× removes; Add to group lists the groups of the contact's address book it isn't in, writable books only — `domain/groupMembership`), and an Events section over `item_attendees` (`useContactEvents`, keyed `['cal.item', 'byContact', id]`): upcoming soonest-first, then past, five rows with Show all; a row opens `ItemDetail`. Its Add to event opens a mirror search (`AddToEventSheet` over `searchItems`) that queues an `item.invite`.
- Calendar has no toolbar: the header title is the period (tap = date picker) and three icons — Search, Today, Month↔Week — sit beside the avatar (`useCalendarHeader`, via `setOptions`) — the grid needs the rows, and Today and the mode switch are used too often for an overflow menu.
- `CalendarScreen` owns only anchor and jumps (the Month/Week mode is `prefs.calendarMode`); `MonthPane` (grid + `DaySheet`) and `WeekView` own their paging and selection.
- Month cells draw as many bars as the measured week row fits, then "+N"; capped cells and folded all-day strips leave birthdays out first (`pickShown`, `packLanes` demotion in `@lupira/cal-domain/occurrences`, shared with the web grids).
- Every calendar gesture is RNGH + Reanimated: swipes, the day sheet's drag, and the week's pinch zoom (time axis, persisted as `prefs.weekHourHeight`), with the lanes' ScrollView joined via `Gesture.Native()`; a PanResponder loses that race to the native scroll.
- Both modes page with `usePager`: prev/current/next stay rendered (21 date-keyed columns / 3 month-keyed grids) on an axis fixed at mount, and a swipe only moves the axis, so the neighbour is live under the finger and a step re-renders nothing visible. Never reset the offset on a swipe; a `CalendarJump` (Today, picked date) is the one snap.
- Lanes are laid out in percent of the day so a zoom frame animates one height.
- Search (`ItemSearchScreen`) reads the mirror, not the API, so it works offline.
- An item draws in its own colour (`item_index.color`, `itemColor` in `@lupira/cal-tokens/itemColors`) wherever it is listed (grids, day sheet, search, contact events, hierarchy), else its calendar's (a multi-calendar item draws once; the grids take `displayCalendarId` from `@lupira/cal-domain/calendars`, the lowest-id shown one); birthdays take the Birthdays calendar's (`useCalendarColors`). Calendar pickers and settings show calendar colours.
- Tentative items draw outlined in both modes: a dashed border in the item's colour over a tint of it (`TENTATIVE` in `@lupira/cal-tokens/color`, applied by `ui/calendar/tentative`; uniform width and colour, or Android draws the rounded border solid). The week view dims and strikes through Cancelled ones.
- A tapped occurrence of a recurring event opens as that occurrence (`ItemDetail` `occurrence` = its unmodified start, the `@lupira/cal-domain/seriesOccurrences` key; grid, search, contact events and reminders pass it). See "Recurring events".
- Subscribed calendar feeds draw with the link glyph and open `SubscribedEventDetail` (read-only: title, time, place, status from `subscribed_occurrences`; description, recurrence and the subscription's name online). `CalendarSettings` → a calendar's Subscriptions (`CalendarSubscriptionsScreen`): status per feed and a per-device hide switch (`prefs.hiddenSubscriptionIds`) for everyone; owners refresh, add and edit (`SubscriptionFormScreen`). Management is online-only (`onlineQuery` under `subscriptions`); a mutation or a newly synced feed triggers `engine.sync()`. Not on the bridge, no notifications.
- `ItemDetailScreen`'s Hierarchy section shows "Part of <parent>" and the direct children (title, first date) from `item_index.parent_item_id` (`useItemHierarchy`, keyed `['cal.item', 'hierarchy', …]`); a row opens that item. A parent outside the mirror shows no row.

## Sync

The offline kernel is `@danbro96/lupira-sync-engine` over `lupira-calendar.db` (`data/db/expoDb.ts`; the pre-kernel `lupira-calendar-mirror.db` is deleted on first open). `sync/engine.ts` wires one module per aggregate (`sync/modules/`), pulled in this order:

| Module | Feed | Writes | Index tables |
|---|---|---|---|
| `cal.calendar` | `/api/sync/calendars` (snapshot; seeds a missing standard set) | — | `calendar_index`, view `bridge_calendars` |
| `contact.addressBook` | `/contact-api/sync/address-books` (snapshot; seeds) | — | — |
| `contact.group` | `/contact-api/sync/groups` (snapshot) | `contact.group.*` ops (member add / remove) | — |
| `cal.item` | `/api/sync/items` (occurrence identities normalized to occurrence keys) | `item.*` ops | `item_index` (`color` = the item's own), `item_calendars`, `item_occurrences` (`original_start`, per-occurrence `title`/`status`), `item_attendees`, `item_places`, view `bridge_items` |
| `contact` | `/contact-api/sync/contacts` | `contact.*` ops | `contact_index`, `birthday_occurrences`, view `bridge_contacts` |
| `contact.relationship` | `/contact-api/sync/relationships` | — | `relationship_index` |
| `contact.residency` | `/contact-api/sync/residencies` | `contact.residency.*` ops | `residency_index`, view `bridge_residencies` |
| `contact.placeEntry` | `/contact-api/sync/place-entries` (doc id = place id) | — | — |
| `tasks.list` | `/tasks-api/sync/lists` | — | — |
| `tasks.item` | `/tasks-api/sync/items` | — (edits live in Lupira Tasks) | `task_deadlines` (open deadlines) |
| `cal.subscribedEvent` | `/api/sync/subscribed-events` (snapshot; occurrences expanded server-side over ±365 d) | — (read-only feed mirror) | `subscribed_occurrences` |
| `contact.me` | `/contact-api/me` (one-doc snapshot) | — | — |
| `geo.place` | `/geo-api/places/lookup` (snapshot of the places residencies point at, doc id = the stored place id) | — | — |

- New tasks come from the new-event editor's Event | Task switch (title carried over, due = the tapped day) and from ItemDetail's "Add task" (`TaskCreateScreen`, linked to the event); both share `useTaskComposer` + `TaskFields` and post straight to tasks-api — online-only, no op — and `engine.sync()` pulls them in. The list picker reads the `tasks.list` mirror; from an event, a `task` relation links the event (`@lupira/cal-domain/tasks` `TASK_RELATION`).
- Every change to an input (pulled doc, queued op, discard, ack) recomputes `local = reduce(server, ...ops)` with `domain/mirrorReducers` and rewrites the module's index rows; a deleted doc is `null`. Table DDL and row writers live in `data/indexes/`, the reads over them in `data/queries/`.
- Ops (`domain/ops.ts`) carry `aggregate`/`aggregateId` from `stamp()`; `state/actions.ts` is the write surface, `sync/replayOp.ts` the REST replay (`Idempotency-Key: commandId`). Ops of one aggregate replay in order; a parked or backed-off op holds the ones behind it.
- Residency ops hold on the contact's id, so an address added to a contact created offline waits for that create. A start sends a UUIDv7 `sourceKey`; its residency id is `deterministicIdFor(residencyStreamKey(contactId, key))`, contact-api's `Residency.StreamIdOf` (fixture in `domain/ids.test.ts`). Move-out replays as `POST /residencies/{id}/move-out`, not the wholesale correction.
- Group membership ops hold on the contact's id too, so adding a contact created offline waits for that create. A remove that 404s is done; an add that 404s parks.
- Occurrences are materialized over a rolling horizon (`domain/materialize`, `expandSeries`: excluded and cancelled occurrences left out, moved ones at their new start, per-occurrence title and status in the row); `sync/horizon.ts` keeps it in kernel meta and reindexes `cal.item` and `contact` when it drifts a month. Grid, search, contact events and notification reads COALESCE the row's title and status over the item's.
- Item ops queue per hold key (`calItemModule.holdKeyOf` = the op's `holdKey`, else its item). Ops on a series created by a split the server hasn't confirmed take the hold key of the series it continues (`sync/holdKeys` over `data/queries/itemLineage`, set at enqueue by `state/actions` and the bridge drain), so they never replay before the split.
- Prefs and bridge flags are kernel meta keys (`sync/meta.ts`). Signing in as a different account cancels notifications, wipes the engine, resets the bridge and clears the query cache, in that order (`state/auth-store.ts`, `onAccountChange`); a sign-out (not an expired session) resets the bridge too (`beforeSignOut`); a reset that fails there goes to Sentry and the sign-out goes ahead, while one that fails on an account change stops the sign-in. A reset (`sync/bridge.ts` `resetBridge`) empties the stock apps and keeps the integration as the user set it.
- Triggers: `startSyncTriggers` (foreground, reconnect, sign-in) from `App.tsx`; the 15-minute background task is defined in `index.ts` and loads the auth session first. The Android bridge drains its inbox before each push and republishes after each pull (`hooks`).
- `SyncBanner` is expo-paper's `StatusBanner` over `bannerState` (tap → Sync issues); `SyncIssuesScreen` is its `SyncStatusView` over the engine's `parked()`/`sync`/`retry`/`discard` (offline it shows no progress and Sync now only says so). Both, and Settings, read the kernel's status store (`state/useSyncStatus`); none shows a sync in progress while the device is offline. Rejected and client-error sync failures (not offline, server errors or sign-out) go to Sentry once per session each (`sync/failureReporter`; `SENTRY_DSN` in `config/`, empty = off; user id = SHA-256 of the email).
- The bridge never opens the app's SQLite file (a second SQLite copy in the process breaks expo-sqlite's locks and WAL). Each publish hands it `data/queries/bridgeSnapshot` — the `bridge_*` view rows as JSON (`id`, `display_name` for contacts, `contact_id` + `place` for residencies, `state` = the stored `{doc, guards}` JSON); it keeps the last one in `bridge-mirror.json` for OS-scheduled syncs, and `MirrorReader.kt` reads that. `sync/modules/bridgeViews.test.ts` pins the contract. A snapshot goes only when the engine changed a calendar, item, contact, residency or residency place since the last one sent (`markBridgeDirty`), or when native answers `snapshotNeeded`; otherwise `bridgeSyncNow` gets null and republishes the kept file.
- Bridge generation: meta `bridge.generation` and the native `Bridge` prefs hold the same id, and each snapshot carries the one read in its transaction. Native takes a call only when it holds none (adopt) or the same; otherwise it answers `stale`. `removeBridgeAccount` rotates native first (under `BridgeLock`, with the sync adapters: provider rows purged before the account goes, inbox, hints and snapshot cleared), meta second, so a publish in flight across a reset is refused and its snapshot never refills the stock apps; `MirrorSnapshot.read` returns only the stored generation's file. A drain whose generation changed underway enqueues nothing.

## Android bridge

`modules/lupira-bridge` publishes the mirror into the phone's calendar and contacts providers under the Lupira account and captures stock-app edits into a Kotlin-owned inbox (`lupira-bridge.db`); `sync/bridge.ts` drains it into ops (`domain/bridgeTranslate` is the pure half).

- Events: one provider calendar per mirror calendar, one event per item (`_SYNC_ID` = item id, RRULE rows for series). `SYNC_DATA1` = content hash (skip + echo guard), `SYNC_DATA2` = the location published, `SYNC_DATA3` = the EXDATE published. A series repeats in its own zone (`EVENT_TIMEZONE` = the item's zone, UTC for all-day), so it keeps its wall clock across DST; exclusions publish as EXDATE, extra occurrences as RDATE, and each changed occurrence as an exception row (`ORIGINAL_SYNC_ID`, `ORIGINAL_INSTANCE_TIME`, `_SYNC_ID` = `<item id>@<original start ms>`, cancelled = `STATUS_CANCELED`, location by the `SYNC_DATA2` rule). Exception rows the mirror no longer has are deleted. `ProviderRecurrence.kt` is the pure half (JVM-tested).
- Occurrence write-back: a captured row with `ORIGINAL_SYNC_ID` / `ORIGINAL_ID` (an occurrence edited in the stock app, or one of ours) is stamped with its exception `_SYNC_ID` and drains as `item.occurrence` (`translateOccurrenceRow`): a deleted one excludes it, and so does a cancelled one (the stock app's delete of one instance) unless the mirror already has that occurrence Cancelled, where it is an edit that stays Cancelled; anything else becomes its change, and what the mirror already holds is skipped. Deleting a series there also hands over its exception rows; their occurrence ops are dropped from that drain (`withoutOccurrencesOfDeleted`). An EXDATE edited on the series row diffs against `SYNC_DATA3` (`exclusionChanges`) into exclude / restore ops, 1 ms after the row's revise. A pending capture holds back the whole series (`BridgeDb.pendingSyncIds` adds the item id). A captured location equal to what was published (or, without one, to the mirror's label) keeps the place; cleared, it clears; anything else is stored as a label with no place (`locationUnresolved`). A stock-created event with a location starts unresolved the same way. The editor then shows "Needs a place".
- Contacts: raw contacts by `SOURCE_ID` = contact id (name, phones, emails, birthday, notes, "Open in Lupira"), `SYNC1` = content hash. Each current residency whose place `geo.place` has looked up becomes a postal row (address, else the place's name; type Home/Work/Other, Vacation as a custom label) tagged `Data.SYNC1` = residency id, `Data.SYNC2` = the text published. Current = today inside moved-in…moved-out (`FuzzyDates.kt`, same rule as `residencyStatus`).
- Postal edits in the stock app never become ops: a place can't be named there. `postalHints` turns them into address hints in the Kotlin table `contact_address_hint` (`listAddressHints` / `putAddressHint` / `deleteAddressHints`): an edited published address becomes a hint standing in for it (published instead of it, tagged `hint:<id>`), a new address a hint of its own, an edited hint row updates the hint, a deleted hint row dismisses it; a deleted published address is restored on the next publish (`invalidateContacts` drops the contact's hash). Rows the stock app re-inserts without their tags match by text. Hints are local to the phone and cleared when the integration is turned off or reset.
- `ContactDetail` lists hints as "Address needs a place"; `ContactEdit` offers them as "From your phone" chips (× dismisses). A chip adds a new address row typed from the hint (`hintAddressRow`; the old address stays, Remove or Moved out is the user's call); saving the row with a place settles the hint.

## Event editor

`ItemEditScreen`:

- A new event starts on the last-used calendars (`prefs.lastCalendarIds`) with you invited as going — your contact id comes from the mirrored `/contact-api/me` doc (`contact.me`); an `item.invite` op's `accept` ids get an RSVP right after the invite. Events you're not on offer Join (detail) and Add me (`PeopleSheet`). `PeopleSheet` lists matches (name or nickname) right under its search field; the people picked are a chip row (tap = remove).
- Place is a chip row (`ui/places/PlaceChipsRow`): the likeliest places from `usePlacePredictions` (`@lupira/cal-domain/placePrediction` over the mirror's place usage — `data/queries/placeUsage` over `item_places` — the item's place and travel endpoints, each once per occurrence up to today — and attendees — invited people's homes, your household's and your own home, saved places and hotspots over the last 24 months; someone else's home's visits count by the event kind's `homeHistory`, full for Meal/Occasion), the picked one selected with why it was offered underneath, and More…. Predictions work offline.
- More… opens `ui/places/PlaceSearchSheet` over `usePlaceOmnibox` (`placeSearchMachine` + `omniboxSections`): browsing, suggested / homes / saved / frequent; typing (typeahead after 250 ms, online), your places, then addresses (picking one creates the place) and Pick on map. Addresses and the pin read "Needs a connection" offline. A location label without a place (typed in the stock calendar app, or a draft's location) shows under the chips as "Needs a place: “…”", seeds the search and survives Save until a place replaces it or Remove clears it; `ItemDetailScreen` tags it "Needs a place".
- Pick on map is `ui/screens/PinPlaceScreen` on the root stack (also from contact addresses): the map (`ui/map/PinMap`) pans under a fixed centre pin, the name is prefilled from the building under it (`usePinSuggestion`) and required for events (a contact's pin may go unnamed; the server names it). It returns the created place with `popTo(origin, { pickedPlace }, { merge: true })`.
- Title, when, place, description up front; the rare fields are More rows opening `ui/event/*Sheet` (`ui/components/Sheet`).
- Colour (More, `ColorSheet`): Calendar colour (`''`, saved as null) or one of the 11 `ItemColor` swatches; series-level only (not on "this event"), and not for availability items, which draw as bands. `ItemCore.color` undefined keeps it (bridge, one-field writes), null clears it; replay sends it with `colorProvided`.
- One Save = one `saveItem` enqueue: core revise + `item.file`/`item.unfile` + `item.invite`/`item.uninvite`. Participation has no section guard; each invite request carries a key derived from the op's command id + contact, and uninvite removes by contact — neither needs the participation id an offline invite doesn't have yet.
- Reminder (More) is your own reminder for the event — Default (n min) / Off / 5 min … 2 days — saved as an `item.reminder` op on your participation (cal-api `PUT /items/{id}/participants/{pid}/reminder`, guarded per participation like the server; replay finds the participation by contact like respond). Picking one on an event you're not on adds you as going.
- Holding an attendee chip on `ItemDetailScreen` sets their RSVP (Going / Maybe / Not going / No reply) as an `item.respond` op; its replay reads the item to find the contact's participation id, so it works behind an offline invite, and does nothing once the contact or the item is gone.
- Place = a `PlaceSelection` (geo `placeId` + label). cal-api 400s free-text `location` without one unless `locationUnresolved` is set, which stores it as a label with no place (`ItemCore.locationUnresolved`; null clears both) — the bridge's and the editor's way to keep text nothing resolved.
- Timed events carry `startTimezone` (the device's by default; the calendar bridge keeps an existing zone): the server repeats a zoned series on that zone's wall clock, so `@lupira/cal-domain/recurrence` does too. Parity fixtures come from LupiraCalApi `tools/FixtureEmitter` (a UTC UNTIL bounds the instant; a floating or date one, the wall clock).

## Recurring events

An occurrence is named by its unmodified start (`occurrenceKey`, UTC whole seconds; all-day at 00:00Z). The series rules are `@lupira/cal-domain/seriesOccurrences`, at parity with cal-api's fixtures.

- `ItemDetailScreen` with an `occurrence` shows it as it reads (its own time, title, description, status). A changed or deleted one says "Changed from the series" / "Deleted from the series" with Revert. Edit, Cancel and Delete open an `ActionMenu` (`lupira-expo-paper`): This event / This and following / All events. "This and following" is offered only from a rule occurrence after the first (`occurrenceScopes`); at the first one it is the whole series. Deleting or cancelling one event toasts Undo; deleting the following ones or all asks first. Cancel is planned by `domain/cancelPlan` (this event, the following ones as a cancelled continuation, or the whole series from the first occurrence); at an occurrence the series no longer has it cancels nothing and says so. Deleting the following ones reads the series as it is on confirm (`deleteFollowing`): at the first occurrence it deletes the whole series, at one the series no longer has as a later rule occurrence it deletes nothing, says so and stays on the event. A recurring item lists its Changed occurrences (deleted, cancelled, changed), each opening that occurrence, with Revert.
- `ItemEditScreen` `scope`: `this` edits title, times, description and Tentative only (`itemFormFromOccurrence`; saved as the occurrence's change, `occurrenceEdit` — nothing left different restores it). `following` opens the series continuing from the occurrence (`followingSeriesOf`) without Calendars, People and Reminder; Save splits and lands on the new series. `series` is the whole item. The scope holds while the editor is open: a save the series no longer allows there (the occurrence gone, or no longer a later rule occurrence) changes nothing and says so. All-day occurrence times are dates at 00:00Z; an end is the last day.
- Ops (`domain/ops.ts`), all under the core guard like the server: `item.occurrence` (exclude, or a change replacing the previous one, keeping its location label), `item.occurrence.restore` (a 404, the series gone or without that occurrence, is done), `item.split` (`POST /items/{id}/occurrences/{originalStart}/following` with the new series' whole core and a `sourceKey`; null core deletes the following ones). A split enqueues `item.continue` with it: the new series as the server will build it (`continuationOf`: id `continuationId(sourceKey)`, `continuesItemId`, calendars, attendees who haven't left (`leftAt`) under `continuedParticipationId`, every section stamped with the split), so it shows offline at once. Its replay only checks the series exists: a discarded split leaves it 404, parked for discarding too. A stale split is a 409 and parks. A split at a key that is neither the first occurrence nor a later rule occurrence (an extra one, or one the series no longer has) changes nothing on the device.
- A revise that moves a series carries its changed occurrences and its UNTIL bound along (`followDeviations` in `mergeItemCore`).
- Per-occurrence place stays series-only.

## Notifications

Local notifications only (no push), planned from the mirror on the device:

| Kind | Id | Channel | When |
| --- | --- | --- | --- |
| Event reminder | `cal:rem:<item>:<start>` | `reminders` | Events you're on and haven't left: your own Before; else the default lead for timed events you're Going / Maybe to; Off silences. All-day: counted back from the morning time. A moved occurrence reminds at its new start under its own title; excluded and cancelled ones never; a tap opens that occurrence (`item/<id>?occ=`) |
| Morning summary | `cal:day:<day>` | `daily` | Morning time; that day's events in shown calendars that you're on (not left), or that are in a calendar you own (`access` Owner) with no attendee row of yours (multi-day trips and stays with "day k of n"), never availability, cancelled or declined |
| Birthdays | `cal:bday:<day>` | `daily` | Birthday time; one per day, with ages |
| Invited | `rsvp:<item>:invited` | `rsvp` | Shown on the next reconcile after an invitation from the last 48 h; at most five a run |
| Remind to reply | `rsvp:<item>:beforeStart` | `rsvp` | Reply lead before the next occurrence (all-day: 18:00 the day before); once per series |

- Domain: `domain/notificationPrefs` (switches all on by default), `domain/reminders`, `domain/rsvpPrompts`, `domain/notificationPlan` (diff by id + content hash, 14-day horizon, nearest 100, only `cal:` / `rsvp:` ids). Wall-clock times use an explicit zone, so 07:00 stays 07:00 across DST.
- `sync/notifications.ts` reconciles (single-flight; `schedule()` debounces 2 s): engine `afterPull`, `onChange` of items / calendars / contacts / me, app start and foreground, prefs changes, and the background sync task (awaited there). It reads only SQLite (`data/queries/notificationSources`, `item_attendees.reminder_mode/reminder_minutes/left_at`) and kernel meta (`prefs.notify.*`, `notify.asked`, `notify.seeded`, `notify.exact`), so it runs headlessly. Without the permission it does nothing.
- First reconcile marks the invitations already waiting as asked (no backlog); turning "Ask when invited" off keeps doing so. Prompts still on screen for invitations answered elsewhere, cancelled or deleted are taken down.
- RSVP buttons (Going / Maybe / Not going, category `rsvp`, no app launch): App's response listener in the foreground, `NOTIFICATION_TASK` (`index.ts`) when backgrounded or killed. `state/notificationResponses` acts once per tap (`notify.handled.<id>@<delivered>:<action>`, kept 30 days), drops a prompt for another account or an event you're no longer on, otherwise queues `item.respond` and pushes. A tap on the body opens its `lupiracalendar://` link (linking `getInitialURL` / `subscribe` read the notification response).
- Exact alarms: `USE_EXACT_ALARM`. If the OS still denies them, every reconcile re-arms fires due within 2 h, and a change either way reschedules everything.
- `NotificationSettings`: the switches, default lead, morning / birthday times, reply lead; a row to allow notifications (system prompt the first time, app settings after); a note when exact alarms are off. Channels and the action category are created before the one-time permission prompt (`data/notifications/setup`).
- Signing in as another account cancels and dismisses everything this app scheduled and forgets what was asked.

## Opening from other apps

`IntentRouterActivity` (lupira-bridge, invisible) turns what other apps send into an in-app deep link (`lupiracalendar://`, linking config in `App.tsx`):

| Intent | Deep link |
| --- | --- |
| VIEW an event row (`vnd.android.cursor.item/event`) | ours (account `com.lupira.calendar`, real `_SYNC_ID`) → `item/<id>`, an exception row → `item/<id>?occ=<original start>`; anyone else's → re-sent to the system calendar app |
| EDIT one of our events | `item/<id>/edit` (an exception row: `?occ=<original start>&scope=this`) |
| INSERT/EDIT any other event (`CalendarContract` extras) | `draft/event?begin=&end=&allDay=&title=&location=&description=&recurrence=` (epoch ms) |
| INSERT a contact (`ContactsContract.Intents.Insert` extras) | `draft/contact?name=&phone=&email=&company=&notes=` |
| VIEW a shared calendar or contact file | `import/<calendar\|contacts>?file=<uuid>` |
| "Open in Lupira" contact row | `contact/<id>` |

- `?occ=` names an occurrence; the linking config's `getStateFromPath` reads it as the `occurrence` route param.
- Shared files are copied to `cacheDir/imports/<uuid>` (5 MB cap; over it, a toast and nothing opens). `readImport` hands the text over once; `clearImports` at app start drops files left by earlier runs.
- `ImportScreen` posts the text to `POST /api/items/drafts?zone=<device zone>` (`text/calendar`) or `POST /contact-api/contacts/drafts` (`text/vcard`), which answer with drafts (`data/imports.ts`, raw body through `apiRequest` — the generated fetchers JSON-encode a string body); it needs a connection. A 400 reads "can't be read", a 413 "too large". Item drafts' locations become places through the place typeahead, or move into the description. One draft opens the editor pre-filled; several show a checklist and a calendar / address-book choice, then one create per draft keyed by its opaque per-user `sourceKey`, so importing again changes nothing.
- Drafts (`domain/drafts.ts`) pre-fill `ItemEditScreen` / `ContactEditScreen` as a new, unsaved entry. A screen opened this way can be the only one in the stack; leaving it lands on the tabs (`leaveScreen`).
- App Links: `https://cal.lupira.com/items/<id>` and `/contacts/<id>` open the app (`app.json` `intentFilters`, `autoVerify`). The BFF serves `/.well-known/assetlinks.json` with the signing-certificate fingerprints from `AppLinks:Sha256Fingerprints`.
- Android asks which app handles a calendar or contact intent the first time; picking Lupira Calendar and "Always" makes it the default. An unverified App Link domain can be enabled under App info → Open by default.
